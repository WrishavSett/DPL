# Multi-Camera Counting Dashboard

A FastAPI-based management dashboard for running YOLO + ByteTrack object
counting across multiple camera sources (RTSP, video files, webcams) with
no system restart required to add, remove, enable, disable, or restart a
camera.

## Architecture at a glance

- **One worker process per camera** (`worker/camera_worker.py`), spawned
  and supervised by `app/camera_manager.py`. A crash or hang in one
  camera's pipeline never affects the others.
- **Counts are event-sourced**, not read from a tracker's in-memory
  cumulative counter. Every line crossing is written as a row to the
  `events` table the moment it happens (`worker/events.py`), so a camera
  restart never zeroes out its counts — restarts only affect what happens
  *after* the restart.
- **A single dedicated DB-writer thread** (`app/db_writer.py`) owns the
  one SQLite write connection; camera workers never open their own write
  connections, which avoids `database is locked` errors under concurrent
  writes.
- **Live frames and status** are published into `multiprocessing.Manager`
  dicts (`app/shared_state.py`) by each worker, and served to the
  dashboard as MJPEG streams (`app/routers/streams.py`) and a WebSocket
  status feed (`app/routers/websocket.py`) — no polling required for the
  live views.
- **Hourly CSV reports** are generated by an APScheduler cron job
  (`app/scheduler.py`) that aggregates the `events` table for the
  completed hour, independent of whatever any camera's tracker state
  happens to be at that moment.

## Project layout

```
app/            FastAPI dashboard: routers, templates, static assets, process lifecycle
worker/         Per-camera process: vision pipeline, event extraction, annotation
db/             SQLite schema
scripts/        One-off utilities (DB bootstrap)
tests/          pytest suite
legacy/         Original single-camera count.py baseline, kept for reference
reports/        Generated hourly CSVs (gitignored)
logs/           Per-camera + main process logs (gitignored)
models/         YOLO weights (gitignored)
```

## Setup

```bash
python -m venv .venv
source .venv/bin/activate          # .venv\Scripts\activate on Windows
pip install -r requirements.txt

cp .env.example .env               # edit as needed
mkdir -p models && cp /path/to/yolo11n.pt models/

python scripts/init_db.py          # optional — app/main.py also does this on startup
```

## Running

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

Then open `http://localhost:8000` for Tab 1 (camera status). Tabs 2–4 are
at `/manage`, `/visualization`, and `/reports`.

No cameras are configured out of the box — add one from the **Manage**
tab, or via the API:

```bash
curl -X POST http://localhost:8000/api/cameras \
  -H "Content-Type: application/json" \
  -d '{
        "camera_id": "cam_01",
        "name": "Front Entrance",
        "source": "rtsp://user:pass@host/stream",
        "classes": ["person"],
        "count_line": {"x1": 0, "y1": 240, "x2": 640, "y2": 240}
      }'
```

## Testing

```bash
pytest
```

Tests mock out heavy dependencies (no real YOLO inference, no real camera
streams, no real `multiprocessing.Manager` where avoidable) so the suite
runs quickly and doesn't need a GPU, a model file, or network access.

## Operational notes / known limitations

- **Per-process model loading**: each camera worker loads its own copy of
  the YOLO model. Fine at the 4-camera scale this was designed for;
  beyond roughly 8–10 cameras on one host, consider a shared inference
  server instead.
- **SQLite, not Postgres**: chosen per the original spec for
  restart-survivability with zero external dependencies. WAL mode plus a
  single writer thread make this comfortable at this scale; a
  high-camera-count deployment would outgrow it.
- **`SCHEDULER_TIMEZONE`** controls both when the hourly cron fires *and*
  how report filenames are stamped. Set it to your deployment's local
  timezone if "system time" in report filenames should mean local
  wall-clock rather than UTC.
- **MJPEG, not WebRTC**: the simplest path to a working N-up grid with no
  extra signaling infrastructure. Latency is a second or two, fine for a
  monitoring dashboard but not for interactive control.
- **GPU device strings** (`"cuda"`, `"cuda:0"`, etc.) are passed straight
  through to Ultralytics — make sure the host actually has a matching
  GPU/driver before setting a camera's device away from `"cpu"`.
